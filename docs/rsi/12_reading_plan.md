## 2. 每篇原文的阅读顺序

先看方法图与算法，标出可变对象、反馈和固定部分；再看实验设置、数据划分、底座、基线及预算；最后看结果与附录中的失败案例。摘要只用于定位主张，不能替代检查主张对应的实验。

每篇记录六行：

```text
问题与假设：
系统边界与可变组件：
质量信号及其来源：
最关键的实验/对照：
结论能支持到哪里：
如果复现，最可能改变结论的因素：
```

对直接 RSI 论文再补三行：新版本怎样参与后续改进；元能力是否单独测量；独立任务/底座迁移是否成立。

## 3. 八周建议安排

这是可以按空闲时间压缩或延长的计划，不是对实验时长的保证。

| 周 | 任务 | 可检查产物 |
|---|---|---|
| 1 | 概念、STaR、Reflexion、自纠错反例 | 一页系统边界定义；三种“自改进”的区别 |
| 2 | STOP、ADAS、SICA、DGM | 四个算法的流程重画；实验协议对照表 |
| 3 | HGM、Hyperagents、过优化及近期评估 | 一个可证伪的问题；最相关工作的差异表 |
| 4 | 实现固定底座、固定改进器基线 | 可重放日志；开发/选择/审计划分；成本估计 |
| 5 | 复现一个关键现象 | 多次运行结果；与原文差异说明 |
| 6 | 加入唯一主要改动 | 组件消融；等预算对照 |
| 7 | 未见任务与任务流验证 | 泛化、负迁移与失败分析 |
| 8 | 整理结论与下一阶段实验 | 图表、方法草稿、局限与复现说明 |

## 4. 三档资源下怎样选择

**没有训练 GPU**：冻结底座，用本地可运行模型或已有 API，研究提示、记忆、工具和元策略。先用少量可执行任务估算成本，不直接启动大规模 SWE-bench 搜索。能够支持方法原型与评价研究，但结论应限定规模。

**有少量训练资源**：在完成推理侧基线后，研究小模型的成功轨迹训练、裁判校准或课程生成。必须同时报告底座、精度、上下文长度与训练 token，不能用参数量单独推算可行性。

**有集群与充分预算**：研究课程/求解器联合训练、跨底座元改进与自动研究。但预算增加之前，应已经有小规模证据说明要测什么、怎样排除替代解释。

## 5. 复现时最容易踩的坑

- 论文的首稿、会议版本和当前仓库实现不一致；要锁定版本。
- API 模型更新或解析格式变化，导致复现并非原设置。
- 开发集多次使用后仍称为测试集。
- 只报告最好一次搜索，忽略失败运行和搜索成本。
- 把重复尝试后的成功率与单次生成 pass@1 混比。
- 把修复已见任务当作泛化，或把代码变化数量当作能力提升。
- 只复现最后分数，没有复现关键机制对照。

这些问题分别对应 [09 评价](09_evaluation.md) 和 [14 证据说明](14_methodology.md)。
